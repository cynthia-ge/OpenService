# OpenService architecture

OpenService is a Java 27 / Spring Boot 4.1.2 application with server-rendered Thymeleaf views and CSS. UI and HTTP API entry points share the same validation, workflow and JDBC storage services. No JavaScript frontend build is required.

`Application.java` starts the server or invokes the private credential setup command. `Store.java` manages PostgreSQL/SQLite connections, schema bootstrap and initial administrator creation. `Migrations.java` serializes startup upgrades and journals ordered schema changes. `Service.java` implements accounts, queries, aggregates, records, workflows and imports. `WebController.java` owns HTTP authentication, CSRF, sessions, attachments and views. `Passwords.java` creates PBKDF2 hashes and verifies existing PBKDF2 and scrypt hashes. `catalog.json` supplies initial table/workflow metadata.

The existing `os_schema`, `os_user`, `os_record`, `os_event` and `os_attachment` tables and JSON record values remain compatible. Each request uses its own connection; mutations commit atomically and failures roll back. PostgreSQL row locks and optional revision ETags protect updates. Attachments (maximum 5 MB each) live in the database. Ordered transactional migrations preserve existing accounts, credentials and records. Startup is serialized on both databases; unsupported or inconsistent migration history prevents startup. Back up the database and use planned downtime before replacing a deployment; rolling upgrades and operational restore targets remain unverified.

Deployment uses PostgreSQL; SQLite is also supported for development. Both database paths run the same HTTP acceptance and workflow tests. Credentials in an existing database continue to work; changing ADMIN_PASSWORD does not reset an existing account. Sessions are server-side and bind to stable, generated user IDs rather than login names. Existing sessions must sign in again after the identity migration. The current-account API exposes only ID, name and role.

This is a single-tenant foundation. Local roles authorize action categories, not individual records or fields. All authenticated roles can read records, notes and attachments. Audit history survives deletion. SSO, granular ACLs, background workers and distributed operation remain future work.

Docker runs the executable JAR as UID 10001. Compose publishes loopback HTTP with secure cookies disabled only for that local demo; Terraform retains HTTPS deployment configurations. The application has no third-party browser scripts, telemetry or AI-provider dependency. Terraform configurations are independent cloud roots, not automatic failover.
